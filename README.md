# DebugMate

> 面向 AI 专业学习场景的多模态报错诊断与复盘智能体（规划中）。

## 项目目的

DebugMate 面向在 Python、深度学习框架和 AI 工程学习中遇到报错的大学生。项目计划让用户提交终端报错文本、报错截图、相关代码片段和环境信息，并获得有依据、可执行且会说明不确定性的诊断建议。

项目的核心价值不是给出看似确定的答案，而是针对真实或可复现的 AI/Python 工程报错，基于专属知识库保留证据链，并从同一份结构化诊断信息派生关联的文字、图像和语音结果。

## 要解决的问题

AI 专业学习中的报错常同时涉及环境、依赖版本、GPU/CUDA、数据格式、框架 API 与代码逻辑。单纯复制报错文本很容易遗漏上下文；只给出一条修复命令又可能误导用户、破坏环境，或无法解释建议的依据。

DebugMate 计划聚焦于以下学习支持场景：

- 接收可脱敏的终端报错文本、截图、代码片段与环境信息。
- 提取异常类型、关键 Traceback、包版本、设备和路径等诊断线索。
- 检索可核验的专属知识库，并将观察到的事实、推断、缺失信息和置信度区分呈现。
- 在信息不足时追问少量高价值信息，或明确说明无法确定，而不是编造根因。
- 将同一次诊断的结果组织为文字报告、确定性 PNG 诊断图和短语音复盘。

## 范围与边界

首版以课程演示闭环和可复现工程资产为目标，而非通用运维平台。计划中的系统不会自动执行 Shell、PowerShell、包安装或修复命令；建议应说明适用环境、潜在影响与回退方式，由用户自行决定是否操作。

项目也不会以生成式插图充当诊断证据，不会把论坛内容直接当作事实知识库，不计划训练自有 OCR、LLM、Embedding 或 TTS 模型，也不同时维护两套正式云端工作流。首版优先支持 Windows 桌面浏览器演示，并优先使用免费额度与本机可用工具；任何付费 API、订阅或云部署都需要另行确认。

## 规划架构

下列内容是技术方向，不代表当前仓库已具备对应能力：

1. **本地入口与安全边界**：计划先对文本和截图完成输入校验与脱敏，再把允许的信息发送到云端。
2. **云端诊断编排**：计划由 Dify Cloud 承担工作流、知识库检索、视觉理解和语音能力的编排，并输出受结构约束的诊断数据。
3. **本地契约与制品**：计划由 Python 适配层用 Pydantic 校验结构化结果，生成可追溯的 Markdown 报告、确定性 PNG 诊断卡、MP3 复盘及运行证据。
4. **统一结果页**：计划使用 Gradio 在同一页面展示脱敏输入、检索依据、报告、图片、音频和下载材料。

计划的数据流为：

`本地脱敏与 Pydantic 校验 → Dify Cloud 工作流 / RAG / 视觉 / TTS → 本地证据、Markdown、确定性 PNG、MP3、Gradio 结果页`

文字、PNG 和 MP3 将共同追溯到同一个结构化诊断对象，而不是由彼此无关的材料拼接而成。

## 计划能力与质量约束

| 方向 | 计划中的要求 |
| --- | --- |
| 可追溯诊断 | 每个根因候选将关联观察证据和知识片段，并区分事实、推断与局限。 |
| 不确定性 | 信息不足时将明确提示，并限制追问数量，避免伪造确定性。 |
| 三模态一致性 | 报告、PNG 与 MP3 将从同一诊断对象派生，并共享可核验的关联信息。 |
| 可复现性 | 知识源、提示词、Schema、工作流导出、评测输入输出和运行证据将纳入版本管理。 |
| 安全边界 | 输入和导出前将默认脱敏；诊断建议不会直接触发外部操作。 |
| 真实性 | 课程截图、演示视频和评测材料只能使用真实运行证据；固定案例回放会明确标注。 |

## 路线图

路线图的权威版本见 [`.planning/ROADMAP.md`](.planning/ROADMAP.md)。六个计划阶段依次为：

1. **Phase 1：工程骨架与平台能力闸门** —— 建立平台无关的数据契约、审计记录与可重建仓库骨架，并进行真实能力探针。
2. **Phase 2：知识库与输入安全** —— 建立可重建的官方知识库以及输入、输出的安全边界。
3. **Phase 3：可追溯诊断工作流** —— 从文本与截图生成带引用、可纠错、说明不确定性的结构化诊断。
4. **Phase 4：三模态产物与统一结果页** —— 从同一诊断对象派生文字、PNG、MP3，并在统一页面展示。
5. **Phase 5：评测、提示词迭代与可靠性闸门** —— 用可复现案例和固定指标衡量质量、安全与一致性。
6. **Phase 6：课程交付自动化** —— 仅从通过质量闸门的真实证据生成课程提交材料。

当前处于 **Phase 1 执行中**；完成情况和待确认的云端能力以 [`.planning/STATE.md`](.planning/STATE.md) 的记录为准。

## 计划技术栈

技术选型详情见 [`.planning/research/STACK.md`](.planning/research/STACK.md)。当前方向包括：

- **Dify Cloud**：计划用于工作流、知识检索、视觉模型调用和结构化输出编排。
- **Python 3.13**：计划作为本地脱敏、适配、校验、制品和证据生成的基础环境。
- **Gradio**：计划用于 Windows 浏览器中的统一输入与结果展示。
- **Pydantic、HTTPX、Pillow**：计划用于严格数据契约、平台调用和确定性图像生成。
- **RapidOCR / ONNX Runtime**：计划用于截图中的本地 OCR 与敏感信息候选识别。
- **pytest、Ruff、FFmpeg**：计划用于质量检查、代码规范与音频有效性校验。
- **edge-tts**：仅作为云端语音路径不可用时的降级方向，并将保留后端标识。

## 隐私与真实证据原则

隐私与真实性不是附加功能，而是项目的基本边界：

- 诊断输入、日志、知识库和交付材料默认应脱敏，优先使用可复现的虚构路径和身份信息。
- 密钥、令牌、密码、邮箱、用户名、绝对路径及其他私有标识不应离开本地或进入版本库。
- 云端平台页面不是唯一事实源；可重建的知识源、提示词、契约、评测与本地证据将优先保存在仓库中。
- 课程展示只应使用真实运行结果；任何回放材料都应清楚标识其性质。
