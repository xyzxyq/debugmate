<action>
Use strict TDD. Add spy providers and tests proving workflow and every CLI/domain entry load/pass the configured approval key and call `verify_approval(approved, approval_key)` before recording `input_approved`. Cover forged signature, expired/stale approval, wrong key, missing configured key, unsafe/escaping screenshot relative path, missing screenshot, and changed screenshot SHA-256; each failure must assert zero extraction, retriever, candidate backend and generation calls. Also prove a valid approval re-resolves the normalized screenshot beneath the configured redacted root and rehashes the same file before its path reaches `ProductionExtractionProvider`. Do not treat Pydantic type validation alone as approval.

Preserve `fixtures/cases/module_not_found/candidates.json` as the primary adapter-compatible dependency/environment candidate fixture. Put the remaining path_permission, python_runtime, tensor_shape_dtype, cuda_memory, model_loading and unknown cases, together with needs-information (at most three questions), second-round insufficient-information, completed diagnosis, generation-failed and correction-rerun variants, into one committed `tests/fixtures/diagnosis/workflow_cases.json` matrix with its own `schema_version`, stable case IDs, expected category/outcome/stages and fixture payloads. Parameterize E2E tests over the primary fixture plus every matrix row so all seven routes and all bounded outcomes remain covered without per-category files. Enforce stages `input_approved -> extracted -> facts_confirmed -> provisional_routed -> sufficiency_checked -> final_routed -> retrieved -> generated -> validated -> published`; approval verification precedes the first named stage, and early outcomes list only completed stages. Prove provisional routing occurs before category-specific sufficiency, accepted answers create a new CaseFacts revision, and final routing occurs afterward.

Implement `DiagnosisRunOutcome` and `DiagnosisWorkflow`. Constructor/entry receives the configured approval key and redacted root; it verifies signature/freshness and screenshot path/hash before any provider call. Then orchestrate extraction, facts, provisional route, sufficiency, accepted-answer revision, final route, validated retrieval and generation. A ready case still receives explicit final routing. Derive idempotency key from facts hash, final rule version, knowledge build ID and Schema version. Correction rerun retains case ID but creates new revision/hash/run/idempotency key and reruns provisional route onward without overwriting old output. Keep `CloudGateway` transport-only.

Add non-interactive CLI/domain JSON boundaries for diagnosis, correction and rerun. Initial output exposes strict ExtractionRecord/CaseFacts views and explicit slots for `exception_type`, `traceback_key_line`, `package`, `version`, `device`, `path`; populated slots include stable IDs, field ID, source, locator and confidence, while missing slots remain explicit. Correction requires case/revision/facts hash, matching field/fact IDs, old-value hash, replacement and reason. Outputs identify backend, revision, run ID and status. Do not add Gradio, report, PNG, MP3/TTS or command execution.
