# Phase 4 自动讨论记录

**日期：** 2026-07-13  
**授权方式：** 用户已明确要求不再逐项询问，由代理持续采用最佳方案。以下选择等同于对推荐方案的批准。  
**讨论边界：** 仅覆盖 `MULTI-01`～`MULTI-05`、`UX-01`～`UX-04`，不进入 Phase 5 评测或 Phase 6 课程包装。

## 1. 三模态生成的权威入口

### 方案 A（采用）：严格 outcome + 已验证 source bundle

读取 `DiagnosisRunOutcome`，严格重验并验证其 Phase 3 source bundle，再取其中 `DiagnosisRecord` 派生产物。

- 优点：同时证明诊断内容、运行身份、阶段状态和证据来源；支持失败、纠错、回放。
- 代价：调用者不能只丢一份 `diagnosis.json`。
- 结论：采用。课程真实性和不可变证据优先于调用便利。

### 方案 B：直接接收裸 `DiagnosisRecord`

- 优点：接口最简单。
- 缺点：不能证明来源 bundle、run ID、回放模式或阶段状态，容易把伪造 JSON 当真实运行。
- 结论：拒绝作为公开入口；仅可在单元测试内部构造严格模型。

### 方案 C：让 Dify 一次生成报告、图和音频

- 优点：平台配置看似集中。
- 缺点：结构漂移、证据不可复建、图中文字不可靠、额度和账号风险高。
- 结论：拒绝。

## 2. 报告与 PNG 的生成方式

### 方案 A（采用）：本地确定性模板 + Pillow

- 优点：不需要新付费模型；事实不漂移；可做 golden/结构测试；Windows 安装面小；能够删除 PNG metadata。
- 代价：视觉表现比生成式设计克制，需要处理中文换行和字体。
- 结论：采用。报告和 PNG 共享一套 presenter/view-model，防止字段排序分叉。

### 方案 B：LLM 改写报告 + 图像生成模型画流程图

- 优点：语言和视觉可能更丰富。
- 缺点：可能增加不存在的建议、错写命令或中文、不能像素级复验，也可能被误认作伪造证据。
- 结论：拒绝。

### 方案 C：Markdown + Mermaid/Graphviz 转 PNG

- 优点：图结构表达自然。
- 缺点：Node/Chromium/Graphviz 和中文字体配置增加 Windows 故障面，课程短周期收益不足。
- 结论：拒绝首版；老师明确要求标准图形语法时再评估。

## 3. PNG 尺寸与长内容

### 方案 A（采用）：固定宽度、计算高度、失败不截断

- 优点：保证文字完整；同版本与字体下布局确定；适合页面预览和下载。
- 代价：极长诊断可能超过安全高度。
- 结论：采用 1600 px 固定宽度、统一换行测量；超过安全高度显式 `png_layout_failed`，不静默裁剪。

### 方案 B：固定 16:9 并自动缩小字体

- 优点：适合幻灯片。
- 缺点：长内容会变得不可读，教师截图难以辨认。
- 结论：拒绝。

### 方案 C：多张 PNG 或 PDF

- 优点：可容纳任意内容。
- 缺点：偏离 `MULTI-02` 的单一诊断卡和当前 Gradio 展示范围；增加打包规则。
- 结论：首版不采用。

## 4. MP3 后端与时长控制

### 方案 A（采用）：Dify → edge-tts → SAPI/FFmpeg

- 优点：优先验证正式平台能力；免费网络降级和完全本机降级都可用；结果明确记录实际后端。
- 代价：三个适配器都需要窄合同与测试替身。
- 结论：采用既定顺序。每个后端都必须经过文件头、ffprobe 和 30–60 秒门禁。

### 方案 B：只使用 edge-tts

- 优点：实现较少，中文效果通常较好。
- 缺点：非官方 SDK、依赖未公开服务行为，失效时没有现场降级。
- 结论：拒绝作为唯一后端。

### 方案 C：只使用 Windows SAPI

- 优点：无需额外密钥，Windows 本机可用。
- 缺点：声音质量和机器安装 voice 不一致，需要 FFmpeg 转码。
- 结论：仅作为最终降级。

## 5. 结果目录和下载包

### 方案 A（采用）：独立 result bundle + 确定性 ZIP

- 优点：不修改 Phase 3 不可变 evidence；完整/部分/回放都有独立 manifest；可验证后再下载。
- 代价：需要 source/run/result 三层关联。
- 结论：采用 `results/<case_id>/<result_id>/`，ZIP 从验证后的 result bundle 生成。

### 方案 B：把报告、PNG、MP3 追加到原 run 目录

- 优点：目录看起来集中。
- 缺点：破坏已封存 manifest 和哈希，违背 Phase 3 原子不可变证据。
- 结论：拒绝。

### 方案 C：浏览器临时生成 ZIP

- 优点：不保存额外目录。
- 缺点：刷新即丢失，无法复核，课程材料不可追溯。
- 结论：拒绝。

## 6. UI 信息架构

### 方案 A（采用）：单页紧凑工作台

顶部状态条；主体按“输入与抽取 / 诊断与证据 / 三模态结果”组织；回放、失败、降级和下载均在当前页完成。

- 优点：符合老师演示的连续叙事；少跳转；状态和证据可同时看到。
- 代价：需用 accordion/tab 控制信息密度。
- 结论：采用，桌面 1366×768 为首要验收视口。

### 方案 B：多步向导

- 优点：每屏信息少。
- 缺点：复查和录屏需要频繁跳转，难以同屏证明三模态一致。
- 结论：拒绝。

### 方案 C：营销首页 + 独立应用页

- 优点：外观完整。
- 缺点：与课程工具目标无关，增加装饰和人工工作。
- 结论：拒绝。

## 7. 回放和失败状态

### 方案 A（采用）：统一状态模型、显式模式徽标

- 优点：同一 UI 可恢复实时、回放、部分成功和失败；不会把 fixture 说成云端成功。
- 代价：需要严格状态转换和组件可见性矩阵。
- 结论：采用 `idle/running/completed/partial/failed/replay`，并同时显示已完成阶段、失败节点、可重试范围和可用降级产物。

### 方案 B：回放使用独立页面

- 优点：逻辑隔离。
- 缺点：页面重复、行为易漂移，录屏前需要维护两套展示。
- 结论：拒绝。

### 方案 C：失败只弹 toast

- 优点：实现简单。
- 缺点：刷新后不可追溯，无法解释部分结果或课程演示中的真实限制。
- 结论：拒绝。

## 8. 自动批准结论

代理根据用户的持续授权锁定方案 A 组合：严格 outcome/source bundle、确定性报告与 Pillow PNG、三级 TTS 降级、独立 result bundle、紧凑 Gradio 单页和统一可恢复状态模型。该组合最符合低人工投入、Windows、免费/本地优先、真实证据和多模态一致性要求。
