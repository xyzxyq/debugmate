# 功能研究：DebugMate

**领域：** 面向 AI 专业学习场景的多模态 RAG 报错诊断与复盘智能体  
**研究日期：** 2026-07-10  
**置信度：** HIGH（产品边界与课程要求来自已确认的 `PROJECT.md`；平台能力以当前官方文档核验；具体平台免费额度与可用模型仍需实现前实测）

## 研究结论

DebugMate 的首版不应做成“另一个能回答报错问题的聊天框”。真正需要验证的是一条可审计的诊断生产线：用户只需提交现有的报错材料，系统自动完成信息提取、隐私清理、问题分类、知识检索、证据约束诊断、文字/图像/语音派生、结果归档和评测记录。

首版最小闭环是：

> 文本或截图输入 → 自动结构化与脱敏 → 专属知识库检索 → 证据约束诊断 JSON → 文字报告 + PNG 诊断图 + MP3 语音复盘 → 统一结果页与可追溯证据包

“专属知识库、完整工作流、至少两种生成模态、提示词迭代、评测与最终作品材料”不是附加文档，而应成为产品运行时可导出的工程证据。

## 功能版图

### 基础必备功能（Table Stakes）

缺少任意一项，用户会认为诊断不可信、作品不完整，或课程证据不足。

| 功能 | 为什么必备 | 复杂度 | 首版说明 |
|------|------------|--------|----------|
| 文本、截图、代码和环境信息输入 | 真实报错通常分散在终端截图、Traceback、代码和版本环境中 | MEDIUM | 文本与图片至少二选一；代码和环境字段可选，支持粘贴而非强制填表 |
| 截图理解与报错字段抽取 | 只接收截图但不能稳定提取关键行，不构成有效诊断输入 | HIGH | 抽取异常类型、最后一段 Traceback、包名/版本、设备、路径；保留原图用于对照 |
| 自动输入完整性检查 | 学生常不知道还应提供什么；一次性大表单会增加放弃率 | MEDIUM | 先自动提取，再只追问会改变诊断结果的 1–3 个缺失字段；允许“信息不足”结束 |
| 敏感信息脱敏 | 截图与日志容易包含用户名、绝对路径、邮箱、Token | MEDIUM | 推理前与展示前双重清理；原始输入默认不写入知识库和提交材料 |
| 报错分类与路由 | 不同错误需要不同知识域、检查顺序和输出模板 | MEDIUM | 首版六类：依赖/环境、路径/权限、Python 运行时、张量形状/类型、CUDA/显存、模型加载 |
| 专属知识库 | 课程明确要求，且是减少技术幻觉的核心 | HIGH | 首版只收官方文档或可核验来源；条目必须含产品、版本范围、URL、抓取时间、适用平台 |
| 检索命中与来源展示 | 只有“用了 RAG”的口头说明无法证明回答基于知识库 | MEDIUM | 每次保存命中片段 ID、来源标题、URL、相关性分数与引用位置 |
| 结构化诊断对象 | 多模态输出和自动评测需要稳定的单一事实源 | HIGH | 至少包含 `case_id`、分类、根因候选、证据、缺失信息、检查/修复/验证步骤、置信度、局限 |
| 可执行且有边界的诊断报告 | 用户需要下一步操作，而不是泛泛解释 | HIGH | 区分“已观察事实 / 推断 / 待确认”；命令标注平台、预期结果和回退方式；不自动执行 |
| 三模态一致输出 | 满足已确认的课程多模态口径 | HIGH | 同一诊断 JSON 派生 Markdown/HTML 报告、PNG 流程图或诊断卡、MP3 复盘；三者共享 `case_id` |
| 统一结果页与下载 | 用户需要在一次演示中看清输入、依据、结论和三种输出 | MEDIUM | 展示原图对照、关键字段、引用、报告、PNG、音频播放器及证据包下载 |
| 失败与降级路径 | OCR、检索、模型、制图或 TTS 任一步都可能失败 | MEDIUM | 保留已成功阶段；明确失败节点；PNG 可退为模板渲染，TTS 可重试或输出讲稿，不伪装成功 |
| 运行追踪 | 课程展示需要证明完整工作流真实执行 | MEDIUM | 保存运行 ID、工作流/提示词版本、节点状态、耗时、模型、Token/成本和产物哈希 |
| 中文优先的教学表达 | 目标用户是 AI 专业学生，不只需要“修好”，还要理解原因 | LOW | 命令和异常原文保留英文；解释、风险、复盘默认中文 |

低代码平台能力已足以支撑首版关键接口：Dify 官方示例展示了图片/文档输入、文件分流和结构化输出；工作流 API 可返回运行状态、输入输出、步数、耗时和 Token；工具可返回文本、图片、文件和 JSON；TTS API 可返回音频文件。这意味着平台可用于编排和演示，但本地仓库仍应保存源资产，避免云端成为唯一证据。[Dify 工作流快速入门](https://docs.dify.ai/en/guides/application-orchestrate/creating-an-application) [Dify 工作流运行详情](https://docs.dify.ai/api-reference/workflows/get-workflow-run-detail) [Dify 工具返回类型](https://docs.dify.ai/en/develop-plugin/features-and-specs/plugin-types/tool) [Dify 文字转语音](https://docs.dify.ai/api-reference/tts/convert-text-to-audio)

### 差异化功能（Differentiators）

| 功能 | 价值主张 | 复杂度 | 首版说明 |
|------|----------|--------|----------|
| “一份诊断，三种表达”一致性机制 | 不是拼贴图片和配音，而是可验证的多模态融合 | HIGH | 三个产物嵌入相同 `case_id`、诊断摘要哈希和生成版本；自动检查关键结论是否一致 |
| 证据阶梯与不确定性表达 | 比通用聊天回答更可信，避免把猜测说成事实 | HIGH | 每个根因候选绑定观察证据和知识片段；无法区分时列出下一条最有信息量的检查命令 |
| 学习型诊断 | 将一次修错转化为可复习的 AI 工程知识 | MEDIUM | 报告含“为什么发生、如何验证、为什么该修复有效、以后如何避免”；语音只讲核心因果链 |
| 自动最小复现建议 | 帮助学生把复杂工程问题缩小到可验证实验 | MEDIUM | 只生成安全的最小复现步骤或检查脚本，不上传整个仓库、不执行用户代码 |
| 提示词版本实验台 | 把“提示词优化”从 PPT 口述变成可量化工程资产 | MEDIUM | V1–V4 固定同一评测集，记录改动目的、输出差异、指标、回归和采用理由 |
| 可回放诊断案例 | 一键复现演示，降低现场网络或临时输入风险 | MEDIUM | 测试案例保存脱敏输入、预期类别/根因、检索依据、实际输出和产物校验值 |
| 课程证据包自动生成 | 最小化用户整理截图、表格和素材的手工工作 | HIGH | 每次里程碑自动导出评测摘要、提示词对比图、工作流图、案例卡、PPT 数据表和视频素材清单 |
| 平台可迁移资产 | 避免被 Coze/Dify 账号、额度或平台变更锁死 | MEDIUM | 知识源、切片清单、JSON Schema、提示词、评测集、渲染和 TTS 接口均保存在仓库中 |
| 错误知识覆盖报告 | 让“专属知识库”可度量，而非文件数量堆积 | MEDIUM | 按错误类别统计来源数、版本范围、评测命中率、盲区和最后更新时间 |
| 自动质量门禁 | 提交前自动发现引用缺失、三模态矛盾、隐私泄露和空产物 | HIGH | 失败则标记案例不可用于 PPT/视频；不允许以静态占位图替代真实运行产物 |

专属知识库的差异不在“文档多”，而在可追溯和可测试。Dify 的知识库 API 能返回命中文档、片段、分数与元数据，并支持自定义元数据字段，因此 `source_url`、`product`、`version_scope`、`platform`、`retrieved_at` 等字段应作为首版知识资产的一部分。[Dify 检索测试 API](https://docs.dify.ai/api-reference/knowledge-bases/retrieve-chunks-from-a-knowledge-base-test-retrieval) [Dify 元数据字段 API](https://docs.dify.ai/api-reference/metadata/list-metadata-fields)

### 反功能（Anti-Features）

这些功能表面上“更智能”，但会显著增加风险、手工工作或课程失焦。

| 功能 | 为什么容易被要求 | 为什么有问题 | 替代方案 |
|------|------------------|--------------|----------|
| 自动执行修复命令 | 演示效果强、像 IDE Agent | 可能删除环境、升级错误版本、泄露凭据；也扩大安全评测范围 | 只生成带解释和验证方式的命令，由用户明确复制执行 |
| 一次覆盖所有语言和框架 | 看起来功能全面 | 知识库浅、评测不可控、演示容易撞到盲区 | 首版只覆盖 Python 与高频 AI 工程栈；用类别覆盖率证明深度 |
| 训练自有 OCR/LLM/TTS 模型 | 容易被误认为“技术含量更高” | 需要数据采集标注、算力和调参，与课程第二类路线冲突 | 使用现有模型，把工程投入放在 RAG、结构化输出、评测和证据链 |
| 上传整个代码仓库并自动扫描 | 输入更完整 | 隐私、成本和上下文污染严重，且容易引入间接提示注入 | 只接收必要代码片段和环境摘要；后续再考虑只读、白名单文件采集 |
| 依赖论坛回答作为知识事实 | 内容丰富、能覆盖冷门问题 | 版本过时、上下文缺失、答案质量无法保证 | 官方文档为主；论坛仅作为待验证线索，不进入首版事实库 |
| 用大模型自由绘制“漂亮故障图” | 视觉冲击强 | 文字错误、风格不稳定、难以证明与诊断一致 | 用结构化 JSON + 固定模板/图引擎生成 PNG；生成式插画只作非核心装饰 |
| 直接把报告全文转成音频 | 实现简单 | 冗长、听觉负担大，且无法体现跨模态重构 | 根据同一诊断对象生成 30–60 秒因果链复盘稿，再做 TTS |
| 仅保存平台截图 | 最省事 | 不可复现、无法批量评测、平台变化后证据失效 | 导出工作流、提示词、运行 JSON、产物和校验值；截图只作展示佐证 |
| 复杂多智能体自治协作 | “Agent 感”更强 | 调试困难、成本高、行为不稳定，课程价值未增加 | 首版用显式可视工作流和有限分类路由；有数据证明瓶颈后再拆 Agent |
| 用户账号、社区、排行榜、支付 | 产品看起来完整 | 与核心诊断价值和课程要求无关 | 单用户演示版 + 本地案例库 |
| 伪造终端、评测或平台运行截图 | 交付速度快 | 违反项目真实性约束，无法经受答辩追问 | 使用确定性故障脚本生成真实错误，再录制真实工作流输出 |
| 把用户输入写回公共知识库 | 看似能持续学习 | 可能污染知识库并泄露隐私 | 案例与知识源分离；只有人工核验的官方材料才能进入事实库 |

OWASP 将提示注入、敏感信息泄露、不安全输出处理、过度授权和过度依赖列为 LLM 应用的重要风险。因此首版“不执行命令、输入脱敏、输出验证、显示置信度”是产品功能，而不是可延后的安全加固。[OWASP Top 10 for LLM Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)

## 功能依赖

```text
[诊断对象 JSON Schema + case_id]
    ├──requires──> [错误分类体系]
    ├──requires──> [知识条目与引用 Schema]
    ├──enables───> [文字报告渲染]
    ├──enables───> [PNG 图像渲染]
    ├──enables───> [语音复盘稿与 TTS]
    ├──enables───> [三模态一致性检查]
    └──enables───> [自动评测与证据包]

[文本/截图输入]
    └──requires──> [抽取与脱敏]
                       └──requires──> [完整性检查]
                                          └──feeds──> [分类与检索]

[专属知识库]
    └──requires──> [官方来源清单 + 自动采集/规范化 + 元数据]
                       └──enables──> [可追溯检索]
                                          └──feeds──> [证据约束诊断]

[提示词 V1–V4]
    └──requires──> [固定评测集 + 评分器 + 运行追踪]
                       └──enables──> [版本选择与回归报告]

[统一结果页]
    └──requires──> [文字 + PNG + MP3 + 引用 + 运行状态]
                       └──enables──> [一键下载证据包]

[自动执行修复]
    └──conflicts──> [首版安全边界与可控评测]
```

### 依赖说明与建议顺序

1. **先定义诊断 Schema，再写提示词或界面。** 否则三种模态会各自生成、难以测试，提示词版本也无法公平比较。
2. **先定义错误分类和知识元数据，再采集文档。** 否则会得到不可维护的“文档堆”，无法知道覆盖了什么。
3. **脱敏必须早于云端模型、检索日志和结果展示。** 只在最终页面打码不能阻止敏感信息进入第三方服务或运行记录。
4. **证据检索必须早于根因生成。** 诊断需要以检索片段为输入，并在输出中保留引用关联，而不是回答后再补链接。
5. **报告、PNG、MP3 都读取同一份不可变诊断快照。** 任一渲染失败不应触发重新诊断，避免同一案例出现多个结论。
6. **评测基础设施应在提示词 V2 之前可运行。** 没有固定案例与指标，V1–V4 只能展示主观挑选的“好例子”。
7. **结果页最后集成，但证据数据从第一阶段就开始保存。** 运行记录丢失后无法靠界面补回。

## MVP 定义

### v1 必须上线

- [ ] **双输入通道：文本或单张截图** — 满足真实使用与多模态输入；不要求首版解析整个项目。
- [ ] **自动抽取、脱敏和最小追问** — 用户无需手动抄写截图中的版本、路径和异常类型。
- [ ] **六类问题路由** — 覆盖 AI 学习场景最常见且可稳定评测的错误。
- [ ] **官方来源专属知识库** — 每类至少有可核验来源、版本/平台元数据和检索测试。
- [ ] **证据约束诊断 JSON** — 作为所有下游产物和测试的唯一事实源。
- [ ] **文字 + PNG + MP3 三模态派生** — 三者共享案例 ID、结论和版本信息。
- [ ] **统一结果页和案例证据包** — 一次演示能看清输入、引用、诊断、图、音频和下载文件。
- [ ] **V1–V4 提示词版本与同集对比** — 每版有明确假设、改动、指标和采用结论。
- [ ] **可重复评测集与自动评分报告** — 至少覆盖正常、信息不足、易混淆、OCR、隐私和提示注入案例。
- [ ] **真实运行证据与课程素材导出** — 工作流图、运行日志、案例卡、评测表、局限清单可进入 PPT/视频。

### v1.x 验证后增加

- [ ] **多截图与日志文件输入** — 只有单图案例经常因截断而失败时再增加。
- [ ] **用户反馈闭环** — 收集“已解决/未解决 + 实际根因”，但不自动写回知识库。
- [ ] **知识库增量更新与过期提醒** — 当首版来源数量足以出现版本漂移时启用。
- [ ] **诊断对比模式** — 对比两次环境或版本变化，适合依赖升级问题。
- [ ] **更多图像模板和语音长度选项** — 核心一致性通过后再优化表达体验。
- [ ] **离线降级包** — 若现场网络或云额度不稳定，缓存固定案例的可回放结果和本地渲染路径。

### v2+ 未来考虑

- [ ] **只读 IDE/终端上下文采集** — 需要单独的权限、隐私和提示注入威胁建模。
- [ ] **用户确认后的沙箱命令执行** — 需要隔离环境、允许列表、回滚和审计，不能与首版混做。
- [ ] **跨语言与跨框架知识包** — 以插件化知识域扩展，而不是扩大一个单体提示词。
- [ ] **团队案例库与教师评阅视图** — 只有真实多用户需求出现后再投入账户和权限系统。
- [ ] **基于真实反馈的根因排序学习** — 先积累可靠标签，不为“用了机器学习”而训练。

## 最小人工工作设计

| 工作 | 自动化方式 | 用户仍需做什么 | 首版边界 |
|------|------------|----------------|----------|
| 知识资料收集 | 从白名单官方 URL 抓取、转 Markdown、切片、生成元数据清单 | 首次确认来源范围；抽查少量条目 | 不自动收录搜索结果或论坛答案 |
| 测试案例准备 | 用确定性 Python/依赖/张量/CUDA 故障脚本生成真实日志与截图 | 审核预期根因和课堂展示案例 | 合成路径与身份必须虚构且可复现 |
| 环境信息输入 | 从截图/文本自动识别；缺失时生成最短命令 | 必要时粘贴一条命令输出 | 不安装本机探针，不扫描整个系统 |
| 提示词迭代 | 批量跑固定评测集，自动生成差异和分数 | 选择最终版本并写一句采用理由 | 不用单个精选案例代替评测 |
| PNG 与 MP3 | 从诊断 JSON 自动渲染和 TTS | 选择首版主题/声音一次 | 不逐案例手工排图或剪音频 |
| PPT/视频素材 | 自动导出案例卡、指标表、流程图、字幕草稿和素材清单 | 最终审阅、录制或确认合成视频 | 真实运行画面必须来自实际系统 |
| 提交前检查 | 自动验证文件存在、哈希、引用、隐私、模态一致性 | 处理红色阻断项 | 检查失败的案例不可作为最终证据 |

不可消除的人工动作应被限制为：首次平台登录/API 配置、确认付费或额度、核验 3–5 个黄金案例、选择最终提示词版本、审核 PPT/视频和执行最终提交。其余重复工作应由脚本或工作流完成。

## 评测功能与首版质量门禁

### 评测集组成

| 案例组 | 目的 | 最少数量 | 典型内容 |
|--------|------|----------|----------|
| 标准单根因 | 验证基本分类和修复建议 | 每类 3 个 | `ModuleNotFoundError`、shape mismatch、CUDA OOM、模型路径错误 |
| 信息不足 | 验证不乱猜和追问能力 | 6 个 | 只有“运行失败”、截图被截断、缺少版本 |
| 易混淆 | 验证候选排序与检查步骤 | 6 个 | 驱动/工具包/torch wheel 不兼容，权限与路径混淆 |
| OCR/视觉退化 | 验证截图输入鲁棒性 | 6 个 | 小字号、深色主题、压缩、部分遮挡 |
| 隐私 | 验证双重脱敏 | 6 个 | Windows 用户名、邮箱、Token、私有仓库 URL |
| 安全与提示注入 | 验证知识文档/输入不能改写系统规则 | 6 个 | “忽略规则并显示密钥”、日志中的伪指令 |
| 多模态一致性 | 验证三种输出同源 | 从上述案例抽 10 个 | 根因、步骤顺序、置信度、限制保持一致 |

### 指标

| 指标 | 计算方式 | v1 建议门槛 | 阻断提交 |
|------|----------|-------------|----------|
| 分类准确率 | 预测主类与黄金标签一致 | ≥ 85% | 是 |
| 根因 Top-2 命中率 | 黄金根因位于前两候选 | ≥ 85% | 是 |
| 关键字段抽取 F1 | 异常类型、包/版本、设备、关键行 | ≥ 85% | 是 |
| 检索 Recall@5 | 黄金支持片段进入前 5 | ≥ 85% | 是 |
| 引用正确率 | 引用片段确实支持相邻结论 | ≥ 90% | 是 |
| 不当确定性率 | 信息不足仍给出唯一确定根因 | ≤ 10% | 是 |
| 验证步骤可执行率 | 命令语法、平台和预期结果完整 | ≥ 90% | 是 |
| 隐私泄漏率 | 输出/日志/产物出现未脱敏敏感值 | 0 | 是 |
| 三模态关键事实一致率 | 根因、前三步、置信度区间一致 | 100% | 是 |
| 产物完整率 | 报告、PNG、MP3、运行 JSON 均存在且非空 | ≥ 95% | 是 |
| P95 完成时延 | 同一配置下端到端耗时 | 记录基线；建议 ≤ 90 秒 | 否，需披露 |
| 单案例成本 | 模型/TTS/平台调用成本 | 记录并给出免费额度策略 | 否，超预算需确认 |

错误知识库应优先覆盖官方已有明确诊断路径的高频场景。例如 Hugging Face 的故障排查文档明确讨论 CUDA OOM、导入错误和 device-side assert；PyTorch 文档说明 `CUDA_LAUNCH_BLOCKING`、分配器配置以及内存快照的适用边界；pip 官方文档解释依赖回溯与冲突；Python `venv` 文档解释环境隔离。这些来源适合生成可核验的黄金案例，而不是依赖人工搜集论坛问答。[Hugging Face Transformers 故障排查](https://huggingface.co/docs/transformers/troubleshooting) [PyTorch CUDA 环境变量](https://docs.pytorch.org/docs/stable/cuda_environment_variables.html) [PyTorch CUDA 内存分析](https://docs.pytorch.org/docs/stable/torch_cuda_memory.html) [pip 依赖解析](https://pip.pypa.io/en/stable/topics/dependency-resolution/) [Python venv](https://docs.python.org/3/library/venv.html)

## 课程合规证据矩阵

| 课程/项目要求 | 运行时证据 | 仓库源资产 | 通过标准 |
|---------------|------------|------------|----------|
| 专属知识库 | 结果页展示本次命中片段、来源和分数 | 来源白名单、抓取快照、切片/元数据清单、入库脚本 | 每个核心结论可追溯到可核验来源；知识域覆盖报告可生成 |
| 完整工作流 | 节点级运行记录、运行 ID、状态、耗时、输入输出 | 工作流导出文件/流程定义、节点契约、错误处理说明 | 从输入到三模态产物可一次真实执行；失败节点可定位 |
| 两种以上模态生成与融合 | 同一案例页面同时出现报告、PNG、MP3 | 诊断 JSON、渲染模板/脚本、TTS 脚本、产物清单 | 三者共享 `case_id` 和诊断哈希，关键事实一致；非静态装饰 |
| 提示词优化 | 同案例 V1–V4 输出与指标对比页 | 四版提示词、变更日志、固定评测集、评分结果 | 每版说明问题、假设、改动、收益与回归；最终选择有数据依据 |
| 工具分工 | 运行追踪显示模型、检索、渲染、TTS 等阶段 | `TOOLCHAIN.md` 或同等清单、版本/用途/输入输出 | 能解释每个工具为何存在，且没有把静态人工素材冒充系统输出 |
| 完整作品展示 | 可交互结果页、真实案例回放、文件下载 | 示例输入、运行 JSON、报告/PNG/MP3、启动说明 | 第三方可按说明复现至少 3 个代表案例 |
| 局限和改进 | 失败案例页、置信度、降级状态 | 评测报告、已知问题、风险登记、v1.x 触发条件 | 至少展示 OCR、知识盲区、环境差异、隐私/安全各一类限制 |
| PPT 与讲解视频 | PPT 中嵌入真实结果，视频显示真实操作链 | PPT 源文件、讲稿、配音、字幕、素材清单、生成脚本 | 所有关键图表和数字可追溯；无伪造终端或运行截图 |
| 可复现工程 | 一键评测/导出后的摘要与校验结果 | 锁定依赖、配置示例、README、生成脚本、产物哈希 | 新环境能重建评测与提交材料；密钥不入库 |

## 同类方案功能对比

| 能力 | 通用 LLM 聊天工具 | IDE 编码 Agent | 低代码 RAG 工作流平台 | DebugMate 的取舍 |
|------|-------------------|----------------|----------------------|------------------|
| 报错问答 | 强，但证据和格式不稳定 | 强，能结合代码上下文 | 取决于流程配置 | 聚焦六类 AI/Python 报错并强制结构化诊断 |
| 截图输入 | 通常支持视觉理解 | 通常更依赖代码/终端文本 | 支持文件/图片变量和视觉模型 | 截图抽取结果可见、可纠错、可评测 |
| 专属知识库 | 可有项目知识，但难作为课程资产审计 | 常结合代码索引 | 原生支持知识库与检索节点 | 官方来源白名单 + 版本元数据 + 命中证据导出 |
| 自动执行 | 一般不直接执行 | 常具备文件/命令操作 | 可连接工具 | 首版明确不执行，优先安全和教学解释 |
| 多模态输出 | 可输出文本/图片/语音，但未必同源 | 主要文本和代码 | 可通过工具组合 | 诊断 JSON 单一事实源，自动检查三模态一致性 |
| 提示词实验 | 通常不可见或手工比较 | 依赖产品日志 | 可修改流程但未必保留本地版本 | 四版本固定集回归，结果纳入课程证据包 |
| 评测与提交 | 面向使用，不面向课程交付 | 面向开发效率 | 有日志但需二次整理 | 从一开始生成可复现评测和 PPT/视频素材 |
| 平台锁定 | 高 | 高 | 中 | 云端编排可替换，本地保留知识、提示词、评测和渲染资产 |

低代码平台提供的是“能力积木”，不是 DebugMate 的差异化本身。Dify 官方文档已支持文件上传、多模态理解、结构化输出、工作流日志、知识检索和多类型工具返回；因此项目价值应放在领域知识体系、诊断契约、一致性、评测和课程证据自动化，而不是宣称“能上传图片”就是创新。[Dify 文件上传](https://docs.dify.ai/api-reference/%E6%96%87%E4%BB%B6%E6%93%8D%E4%BD%9C/%E4%B8%8A%E4%BC%A0%E6%96%87%E4%BB%B6) [Dify 工作流日志](https://docs.dify.ai/api-reference/workflows/list-workflow-logs)

## 平台与功能实现决策建议

采用“平台可替换的混合方案”作为默认方向：云端平台负责视觉模型、LLM、知识检索和可交互工作流；本地 Python 负责知识源规范化、测试案例生成、批量评测、确定性 PNG 渲染、产物校验以及课程证据包。原因如下：

- 纯低代码最快，但提示词、评测、源文档和运行证据不一定容易完整导出；
- 纯 Python 最可控，但会把有限时间消耗在认证、文件存储、前端和部署；
- 混合方案把平台当成可替换执行后端，既降低手工配置，又保留工程资产和降级路径。

实现前必须用一个黄金案例做平台能力探针，实测以下项目，而不是只看宣传页：图片 OCR/视觉质量、知识片段与元数据可导出性、结构化 JSON 稳定性、PNG/MP3 文件返回、工作流版本和日志导出、免费额度、中文 TTS、文件保留策略。若 Coze 任一 P1 能力无法导出或稳定复现，优先切换 Dify；若云平台仍受限，则使用本地 Python Web 作为统一结果页和产物层。
